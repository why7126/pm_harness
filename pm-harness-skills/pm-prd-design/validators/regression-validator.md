# Regression Validator

对比"本版本"与"来自 `source.zip` 的上一版本"，确认未被本次请求（`iteration-request.md` 或 `patch-request.md`）明确覆盖的区域没有发生非预期变化。ITERATE 与 PATCH 模式必跑；PATCH 模式的判定应更严格，因为其允许改动的范围本就更小。

## 检查维度

### 1. 布局（Layout）
- [ ] 页面区块顺序、栅格结构是否与上一版一致（除非改动请求明确涉及布局调整）
- [ ] 页面间的导航结构/层级是否一致

### 2. 组件（Components）
- [ ] 未被要求修改的组件，其样式（尺寸/圆角/间距/状态）是否与上一版一致
- [ ] 未被要求修改的组件，其交互行为是否与上一版一致
- [ ] 没有出现未被要求新增的组件；没有出现被静默移除的组件

### 3. 设计系统（Design System）
- [ ] 配色 token 是否与上一版一致
- [ ] 字体（字族/字号阶梯/行高）是否与上一版一致
- [ ] 间距体系是否与上一版一致

### 4. 关键流程（Workflow）
- [ ] 核心用户路径（如注册/下单/提交审批等主流程）的步骤数和顺序是否与上一版一致
- [ ] 未被要求修改的表单校验规则、错误提示文案是否与上一版一致

## 记录方式

把结果写入 `regression-report.md`，每一项标注三种状态之一，并附一句话说明：

- **未变化**：与上一版本一致
- **已按要求变化**：变化在本次请求的授权范围内，说明对应的请求条目
- **意外变化**：变化不在本次请求范围内 → 判定本次校验不通过，需返回修正

## 判定

出现任何一条"意外变化"，本次交付不能放行，必须回到生成步骤，把该处改回与上一版本一致，或者向用户确认是否要把它纳入本次请求范围后再放行。

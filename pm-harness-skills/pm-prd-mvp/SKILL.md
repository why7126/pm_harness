# PM PRD MVP

把 `pm-prd-plan` 输出收敛为 `pm-prd-design` 可直接承接的 MVP 基线。持续反问、主动挑战假设、保留证据与决策轨迹；未经用户确认不得替用户冻结关键取舍。

## 必读路由

- 每次运行先读 [operating-modes.md](references/operating-modes.md) 与 [convergence-workflow.md](references/convergence-workflow.md)。
- 进行功能取舍或范围冻结时读 [scoring-and-scope-model.md](references/scoring-and-scope-model.md)。
- 定义验收、数据、样本、灰度或退出决策时读 [validation-framework.md](references/validation-framework.md)。
- 建立编号、追踪、版本或 Patch 时读 [traceability-and-versioning.md](references/traceability-and-versioning.md)。
- 生成交付包前读 [output-contract.md](references/output-contract.md)。

## 边界

遵循链路：`pm-prd-position → pm-prd-plan → pm-prd-mvp → pm-prd-design`。

- 输入：默认承接完整产品规划基线包。
- 输出：MVP 目标、假设、闭环、任务链路、范围、优先级、版本、验收、验证、数据、依赖风险和设计交接基线。
- 禁止：重做产品定位或完整规划；定义页面清单、页面布局、字段、组件、视觉和详细交互；把 MVP 简化为删减功能清单。
- 上游缺失：判断是否阻断。阻断项要求补充或返回 `pm-prd-plan`；非阻断项标记事实、假设、待验证项、条件和风险后继续。

## 核心工作流

1. 识别运行模式并校验最低输入。
2. 从定位与规划中提取已确认结论、硬约束、事实、假设和未决项。
3. 按主题分轮反问；根据回答动态跳转、追问和挑战。每轮给推荐项、理由与主要风险。
4. 聚焦每个递进版本的核心用户、场景、任务和待验证假设。
5. 定义目标用户可独立完成、获得核心价值并产生验证结果的端到端最小业务闭环。
6. 对候选功能评分并划分四层范围；展示依据、闭环影响、成本、风险和替代方案，讨论至一致。
7. 按验证顺序拆分递进版本；每版明确目标、范围、成果、准入、退出和回退条件。
8. 分别定义交付验收与假设验证，并补齐数据、样本、灰度、责任、依赖、人工替代和技术债务。
9. 建立从定位到指标的双向追踪；检查阻断性分歧。
10. 完整性检查通过后呈现关键结论、未决条件和风险，取得用户明确确认再冻结版本。
11. 复制 `assets/baseline-templates/` 生成完整基线包，运行校验与打包脚本。

## 强制规则

- 时间、预算、人力、资源容量是硬约束；冲突时重新取舍并让用户确认。
- 证据不足时区分事实、假设与待验证项；阻断问题不得带条件交付。
- 新需求先分析对假设、闭环、指标、依赖、成本和风险的直接及连带影响，再由用户选择纳入、延后或排除。
- 范围冻结后，仅核心闭环、关键验证、合规安全、关键依赖或交付可行性问题可申请变更，统一走 Patch。
- 不得以默认增加功能修复验证失败；必须依据证据选择继续、调整或停止。
- 人工替代不得损害核心价值验证，必须记录容量、成本、风险、数据和自动化替换条件。
- 上线前必须满足闭环验收、关键依赖、数据采集、合规安全、运营异常处置和无阻断风险。
- 未决阻断问题存在时不得宣称收敛完成或交付正式基线。

## 完成条件

仅当核心假设、闭环、取舍、递进版本、验收、验证指标、数据、边界、依赖风险、责任和待设计问题均已确认，且无阻断性分歧，才可结束。向 `pm-prd-design` 交接已确认基线、设计范围、业务闭环、功能架构、角色任务、约束、验收标准及待设计问题，不越界补页面字段和交互。

# 工具知多少（Tool Info Lookup）

给定一个工具/产品名称，联网调研并输出一张包含 17 个固定字段的"工具信息卡片"，让用户快速掌握该工具的基本情况。

## 核心原则

1. **字段必须齐全**：无论用户问题多简短，输出必须覆盖全部 17 个字段，缺一不可。查不到的字段要显式标注"未公开/不适用"，禁止直接省略该字段。
2. **实时性优先**：GitHub 星数等数据必须联网获取当前真实值，禁止凭训练记忆直接给出数字（星数增长很快，记忆里的数字大概率过期）。
3. **一个工具一次调研**：如果用户一次给了多个工具名，逐个调研，最后用同一张字段模板分别输出（可以合并成对比表格，见下方"多工具对比"）。
4. **来源可信优先**：官网 > 官方 GitHub/Gitee 仓库 > 官方文档 > 权威科技媒体/百科 > 一般博客。不确定的信息要标注来源或注明"网络信息，未在官网验证"。

## 调研流程

### 第一步：确认工具名称与消歧

如果工具名称有歧义（比如撞名的多个产品，或者是某个大公司旗下同名功能），先用一次 `web_search` 确认最可能的目标产品，必要时用一句话向用户确认（除非上下文已经足够明确，比如用户已经给了官网链接或说明了行业背景，这种情况直接调研，不必打断用户）。

### 第二步：搜索官方信息源

依次搜索并尽量 `web_fetch` 以下页面（不是每个工具都有全部页面，缺失的正常跳过）：

- 官网首页 / 产品介绍页 / 定价页（pricing）
- GitHub 仓库主页（如果开源或有开源组件）
- Gitee 镜像仓库（国内工具常见，搜索"{工具名} gitee"）
- 官方文档站（docs.xxx.com 或官网的 /docs、/guide 路径）
- 官方 Demo/Playground/在线体验页
- 权威第三方介绍（用于补充分类、标签、是否AI工具等判断依据）

搜索建议的 query 写法（每次 1 个，逐步细化）：
- `{工具名}`
- `{工具名} 官网`
- `{工具名} github`
- `{工具名} pricing` 或 `{工具名} 定价`
- `{工具名} docs` 或 `{工具名} 文档`
- `{工具名} 开源` / `{工具名} open source`
- `{工具名} 本地部署 端口` （如果怀疑支持本地部署，比如自托管软件、开发者工具）

### 第三步：获取 GitHub 星数（重点，务必实时）

找到 GitHub 仓库地址后，**优先用 GitHub API 直接取实时数据**，比网页搜索结果更准更快。当前网络配置已放通 `api.github.com`，可以直接在 bash 里执行：

```bash
curl -s https://api.github.com/repos/{owner}/{repo} | python3 -c "
import json,sys
d = json.load(sys.stdin)
print('stars:', d.get('stargazers_count'))
print('forks:', d.get('forks_count'))
print('description:', d.get('description'))
print('language:', d.get('language'))
print('license:', (d.get('license') or {}).get('name'))
"
```

注意事项：
- `{owner}/{repo}` 从仓库 URL `github.com/{owner}/{repo}` 中提取。
- 如果工具有多个相关仓库（比如前端+后端分开、或者有一个"awesome list"和一个"主仓库"），优先取**官方主仓库**（通常是 star 数最高、且是产品本体代码的那个）。
- 如果 API 请求被限流（返回 rate limit 相关信息）或该工具根本没有 GitHub 仓库，退回用 `web_search`/`web_fetch` 查看仓库页面上显示的星数，并在结果里注明"通过网页读取，可能有延迟"。
- 星数格式化：低于 1 万直接写具体数字（如 8,432）；1 万以上可以用"约 3.2 万"这种表达，但要在括号里保留精确抓取时间，例如"约 3.2 万（截至 2026-07-30 API 数据）"。

### 第四步：整理字段

逐一确认以下 17 个字段，字段释义与判断标准见下表：

| 字段 | 说明 / 判断标准 |
|---|---|
| 工具描述 | 一句话（不超过 40 字）说清楚这是个什么工具，给谁用、解决什么问题 |
| 核心功能点（亮点） | 3-6 条 bullet，突出差异化能力，不要照抄官网营销话术，用自己的话概括 |
| 是否AI工具 | "是" / "否" / "部分功能AI化"，并简要说明判断依据（比如是否内置大模型能力、AI 是核心还是附加功能） |
| 套餐订阅 | 列出主要档位（如 免费版/个人版/团队版/企业版）及大致价格区间；纯开源免费工具写"开源免费，无订阅套餐"；查不到具体价格写"官网未公开具体价格，需联系销售" |
| 工具分类 | 一级行业/领域分类，如"效率协作工具""开发者工具""设计工具""数据分析" |
| 工具子类 | 二级细分类，如分类是"开发者工具"，子类可以是"代码编辑器""API 测试工具""CI/CD 平台" |
| 工具标签 | 5-10 个短标签，便于检索，如 #笔记 #知识管理 #跨平台 #AI写作 |
| 是否开源 | "是" / "否" / "部分开源（核心闭源+插件开源）等" |
| 适用平台 | Web / Windows / macOS / Linux / iOS / Android / 浏览器插件 / 命令行 等，列全 |
| 官网 | 完整 URL |
| GitHub地址 | 完整仓库 URL，没有则写"无公开 GitHub 仓库" |
| GitHub星数 | 见第三步获取方法，附抓取方式和大致时间 |
| Gitee地址 | 完整仓库 URL，没有则写"无 Gitee 镜像" |
| Demo地址 | 官方在线体验/Playground 链接，没有则写"官方未提供在线 Demo" |
| 文档 | 官方文档站 URL |
| 本地默认端口 | 仅当支持本地部署/自托管时填写，如"默认 8080（Web UI），5432（数据库）"；不支持本地部署则写"不适用（无本地部署能力）" |
| 所属公司 | 开发/运营该工具的公司或组织名称，个人开源项目写"个人开发者维护"或具体作者名 |

### 第五步：输出格式

用 Markdown 表格（两列：字段 / 内容）直接在对话中呈现，不要生成 docx/md 文件（这是一次性信息查询，不是要保存的长文档，符合"对话内简短参考信息"原则，除非用户明确要求"整理成文档/导出"）。

输出结构建议：

```
## {工具名} 信息卡片

| 字段 | 内容 |
|---|---|
| 工具描述 | ... |
| 核心功能点 | - 亮点1\n- 亮点2\n- 亮点3 |
| 是否AI工具 | ... |
| 套餐订阅 | ... |
| 工具分类 | ... |
| 工具子类 | ... |
| 工具标签 | ... |
| 是否开源 | ... |
| 适用平台 | ... |
| 官网 | ... |
| GitHub地址 | ... |
| GitHub星数 | ... |
| Gitee地址 | ... |
| Demo地址 | ... |
| 文档 | ... |
| 本地默认端口 | ... |
| 所属公司 | ... |
```

表格后可以补充 1-2 句总结性点评（例如适合什么样的用户/团队），但不要长篇大论，保持信息卡片的简洁性。

## 多工具对比

如果用户一次问了多个工具（比如"对比一下 Notion、Obsidian、飞书文档"），改用"字段为行、工具为列"的宽表格，方便横向比较，字段顺序不变。逐个工具仍按上面流程调研，只是最后合并展示。

## 常见坑

- 不要把"是否AI工具"简单等同于"官网提了AI"：很多传统工具会营销式地提一嘴"AI 功能"，判断时看 AI 是不是产品的核心能力。
- GitHub 星数不要用记忆里的数字直接回答，哪怕看起来很确定，也要走第三步实时抓取，因为热门项目星数每天都在变。
- 同名工具容易搞混（比如很多叫"Copilot"的产品），拿不准时先用一次搜索消歧，比错误调研一个不相关的产品要好。
- 中国大陆工具经常同时有 GitHub 和 Gitee 两个仓库，两个都要查，不要只查 GitHub 就假设没有 Gitee。
- "本地默认端口"只对支持自托管/本地部署的软件有意义（比如 Docker 部署的工具、桌面应用背后跑本地服务的），纯 SaaS 工具这一项直接写不适用，不要瞎编端口号。
